## Chrome team: Modern Web Guidance — https://github.com/GoogleChrome/modern-web-guidance

- **Kind:** Claude skill (SKILL.md) plus CLI retrieval (`npx modern-web-guidance search|retrieve`). It is also packaged as a Claude, Codex, Cursor, Gemini, Copilot and Kimi plugin. It is listed in the official Claude plugin marketplace and in the Cursor marketplace.
- **Signals:** 2,300 stars. Created 2026-03-23. Last push 2026-09-21. The guides are regenerated by a bot (`performance.md` changed on 2026-09-21). skills.sh: 23.3K installs. Announced at Google I/O 2026 by the Chrome team (Parisa Tabriz, Paul Kinlan and others). Apache-2.0. The CLI sends anonymous telemetry (search queries and guide IDs) unless `DISABLE_TELEMETRY=1` is set.
- **Scope and structure:** SKILL.md is about 6.7 KB. It holds a search, retrieve and verify workflow, not rules. There are more than 100 guides in `guides/<area>/`: accessibility, built-in-ai, css, forms, html, js, **performance (23 guides)**, privacy, security, ui-atoms, ui-behaviors, ui-components, visual-design. Each area has one hub file (for example `performance.md`, 20 KB, organized as DOs, DON'Ts and code) plus one file per **use case** (for example `break-up-long-tasks`, `efficient-background-processing`, `interactions-in-complex-layouts`, `identify-inp-causes`, `defer-work-until-scroll-ends`, `optimize-image-priority`). Topics are classified **by developer task**, not by metric or pipeline stage. Each guide ends with a "Fallback strategies" block. This block states the Baseline status and the first browser versions with dates, generated from web-features data.
- **Trigger:** The description is aggressive. It says to run the skill first for every HTML, CSS or client-side JS task, because model weights hold old patterns. It lists trigger areas (UI and layout, scroll and motion, CWV, content-visibility, Fetch Priority) and explicit non-triggers (backend, CI, scripts).
- **Strong rules (paraphrased):**
  - Browser-support policy: Baseline Widely available features need no fallback. Other features **must** follow the guide's fallback, unless the project states its own policy. When the developer names a restricted runtime or a polyfill concern, suggest writing the policy into CLAUDE.md or AGENTS.md.
  - Yield on a **time deadline** (50 ms since the last yield), not every N items. Feature-detect `scheduler.yield()` (Chrome 129, Firefox 142, no Safari) and fall back to a `setTimeout` promise.
  - A work-size heuristic: under 50 ms, run it synchronously. From 50 to 250 ms, slice it and yield. Over 250 ms, move it to a Web Worker.
  - `content-visibility: auto` plus `contain-intrinsic-size: auto <len>` on large self-contained regions (board columns, grid panels). This isolates layout **even while the region is on screen**, because the property applies layout, style and paint containment. It is Baseline newly available since 2025-09-15.
  - Pause canvas, WebGL and polling work when the browser skips rendering a region: listen for `contentvisibilityautostatechange` on the element itself (the event does not bubble everywhere) and check `event.skipped`. Use IntersectionObserver as the fallback.
  - Use `scrollend` instead of a debounced `scroll` handler for heavy work after scrolling. It is Baseline newly available since 2025-12-12.
  - Field INP attribution: use the `web-vitals/attribution` build and beacon the three subparts plus the longest script from Long Animation Frames. LoAF is Chrome-only and needs no fallback, because it only adds detail.
  - Size a canvas from a `ResizeObserver` with `box: 'device-pixel-content-box'`. Fall back to `contentRect × devicePixelRatio`, rounded.
  - Do not use `fetchpriority="high"` on fonts, because fonts already load at high priority. Always add `crossorigin` to font preloads, even for the same origin.
- **Weak points:**
  - It says `Cache-Control: no-store` stops bfcache, as an absolute rule. Chrome finished rolling out bfcache for no-store pages in March–April 2025. Such pages are only evicted on a cookie change, on WebSocket, WebTransport or WebRTC use, or after 3 minutes (developer.chrome.com/docs/web-platform/bfcache-ccns).
  - It recommends the `preload` + inline `onload` swap for CSS. A strict CSP without inline handlers blocks this.
  - It puts `loading="lazy"` on `<video>` without a support note. webstatus shows lazy-loading media only in Chrome/Edge 150 (2026-06-30).
  - It calls JPEG XL "best compression" but does not mention that only Safari supports it (webstatus: `jpegxl` limited, Safari 17 only).
  - The `schedule-tasks-by-priority` fallback loads a polyfill at runtime from unpkg with no SRI. This contradicts its own "self-host third parties" rule.
  - The `identify-heavy-scripts` example regroups the whole growing script list on every observer callback. The work grows with the square of the entries, and memory grows without limit.
  - The HTML-in-Canvas guides mark origin-trial APIs as "MANDATORY", and their render loop calls `requestPaint()` on every frame even when the page is idle.
  - Retrieval runs through `npx` over the network. We cannot use this pattern: our working rules forbid running downloaded code.

## PixiJS team: `pixijs-performance` — https://github.com/pixijs/pixijs-skills/blob/main/skills/pixijs-performance/SKILL.md

- **Kind:** Claude skill (SKILL.md), official vendor.
- **Signals:** Repository 337 stars. File last changed 2026-09-17 (author Zyie). skills.sh: 4.7K installs. MIT.
- **Scope and structure:** One file, 18 KB. The sections are Quick Start, Core Patterns and Common Mistakes, followed by API links. The Common Mistakes are tagged `[CRITICAL]`, `[HIGH]` and `[MEDIUM]`, and many cite the library source file the rule comes from (for example `src/prepare/PrepareSystem.ts`). Topics are classified **by GPU cost type**: destroy and GC, upload, batching, text, culling, resolution, masks.
- **Trigger:** The description starts with profiling and optimizing for FPS, draw calls and GPU memory, then gives a long "Triggers on:" keyword list (jank, draw calls, batching, memory leak, WebGPU performance and others).
- **Strong rules (paraphrased; these transfer to any WebGL/WebGPU chart engine, SciChart included):**
  - Profile first. Only then pick one targeted pattern (destroy, pool, batch, cache, cull).
  - Upload textures and geometry to the GPU **before** the first visible frame. A first-render upload causes a hitch.
  - Text drawn through a 2D canvas is re-rasterized and re-uploaded on every change. Never set it on every frame without a check. Use atlas (bitmap) text for counters and tickers, or compare with the old value first.
  - Draw order changes the draw-call count. Group objects of the same kind and the same blend mode. Alternating kinds breaks batches.
  - Mask cost from lowest to highest: axis-aligned rectangle (scissor), then stencil, then alpha or filter. Use rectangle clips when the bounds are axis-aligned.
  - Culling saves GPU time but costs CPU for bounds checks. Use it only when the app is GPU-bound.
  - Destroying many GPU resources in one frame freezes the frame. Spread the destruction over frames.
  - For large buffers, upload only the changed byte range.
  - Resolution 2 means 4 times the pixels. Decide resolution and antialias on the target hardware.
  - When you know the filter area, set it explicitly, so the engine does not measure bounds on every frame.
- **Weak points:** It is written for a scene graph, so the API names do not transfer directly. "Destroy and recreate is much slower than pooling" has no number attached. It has nothing on main-thread scheduling, input latency or the DOM.

## TradingView: `lightweight-charts` — https://github.com/tradingview/lightweight-charts/blob/master/.github/skills/lightweight-charts/SKILL.md

- **Kind:** Claude skill (SKILL.md) that lives in the library's own repository (`.github/skills/`). There is also a `lightweight-charts-plugin-authoring` skill with 3 reference files.
- **Signals:** Repository 17.3K stars. File last changed 2026-06-04. skills.sh: 1.1K installs.
- **Scope and structure:** 27.6 KB. It starts with a source lookup order, then a "Triage (problem → API → avoid)" table, a v4-to-v5 replacement matrix, recipes, a worked example (symptom, layers, suspect, verify, fix, references), code-generation rules and an answer contract. It is about correctness more than performance, but the performance rules it has are chart-specific.
- **Trigger:** The description lists the tasks: creating charts, adding series, streaming realtime or historical data, panes, markers, plugins, SSR and framework wrappers.
- **Strong rules (paraphrased):**
  - Read the installed package version and typings first. When the typings and the docs disagree, the local typings win. If an API name is not in the installed typings, it does not exist.
  - Realtime: update or append only the last point for each tick. Replacing the whole dataset on each tick resets the view and costs more. To prepend history, rebuild once, then restore the visible range.
  - Create the chart once when the component mounts, and destroy it in cleanup. Recreating it on each render duplicates DOM and leaks listeners.
  - Let the chart size itself with ResizeObserver, or observe the container and call resize. Do not poll.
  - Keep code snippets minimal: one feature per block.
- **Weak points:** It is a different library, so SciChart API names do not map one to one. It has no frame budget or memory numbers.

## ibelick: `fixing-motion-performance` — https://github.com/ibelick/ui-skills/blob/main/skills/fixing-motion-performance/SKILL.md

- **Kind:** Claude skill (SKILL.md).
- **Signals:** Repository 8.9K stars. File last changed 2026-02-19. skills.sh: 23.2K installs. First seen on skills.sh 2026-01-22. It passes all three security audits (Gen Agent Trust Hub, Socket, Snyk).
- **Scope and structure:** 5.6 KB, one file. It is classified **by rendering pipeline stage**: a small glossary maps properties to composite, paint and layout. A 9-row priority table follows: never patterns, mechanism, measurement, scroll, paint, layers, blur, view transitions, tool boundaries. There are two modes: apply to the conversation, or review a file and report each violation as the quoted line, why it matters in one sentence, and a code fix.
- **Trigger:** It fires when animations stutter, when a transition janks, or when you review CSS or JS animation performance. The "when to apply" section also covers adding or changing any UI animation.
- **Strong rules (paraphrased):**
  - Every rAF loop needs a stop condition.
  - Do not mix two animation systems that each measure or change layout on the same element.
  - Do not animate CSS custom properties that feed transform, opacity or position. Do not animate inherited custom properties, because each change invalidates style for the whole subtree. Scope animated variables locally.
  - Compositor motion needs layer promotion, and you cannot assume the browser does it. Use `will-change` for a short time, only where needed, and check the result in tooling.
  - Keep blur animation small (8 px or less), short and one-time. Never animate blur on a large surface.
  - Tool boundary: do not migrate animation libraries unless asked. Apply the rules inside the existing stack.
  - For each non-default choice, state the limit that justifies it (surface size, duration or interaction).
- **Weak points:**
  - Its FLIP example sets the inverse transform and then clears it inside the same `requestAnimationFrame`. No style flush happens between the two steps, so the transition may not run. A forced reflow or a second frame is needed.
  - It gives `animation-timeline: view()` as the fix with no support guard. Scroll-driven animations are "limited" (Chrome 115 and Safari 26, no Firefox).

## Mapbox: `mapbox-web-performance-patterns` — https://github.com/mapbox/mapbox-agent-skills/blob/main/skills/mapbox-web-performance-patterns/SKILL.md

- **Kind:** Claude skill (SKILL.md), official vendor (a WebGL map engine).
- **Signals:** Repository 78 stars. File last changed 2026-07-30. skills.sh: 2.2K installs.
- **Scope and structure:** 11 KB SKILL.md plus 5 reference files (data-loading, interactions, memory, mobile, layers-styles). Rules are prioritized **by user impact** (critical, high, optimization). It ends with a checklist and target metrics.
- **Trigger:** The description covers performance patterns for the map library: startup waterfalls, bundle size, rendering, memory.
- **Strong rules (paraphrased):**
  - Start data fetches **in parallel** with engine start-up. Do not wait for the engine's `load` event before fetching.
  - Pick the rendering path by count: DOM markers below about 100 items, GPU layers up to about 10K, clustering above that, server-side tiling above about 100K.
  - It names an **agent anti-pattern**: first-pass agent code is "happy path only". It has no error handler, no teardown, and a dataset too small to test the feature. Generated code needs all three.
  - Call the engine's teardown (`remove()`) when an SPA view unmounts. Reuse popups. Use feature state for hover and selection instead of adding layers.
  - Do not turn on `preserveDrawingBuffer` or `antialias` without a need.
  - Target: memory grows less than 10 MB per hour of use.
- **Weak points:** It counts `render` events as FPS, so an idle map reads as low FPS. It targets "Time to Interactive", which Lighthouse no longer reports. It debounces handlers as a general fix.

## Microsoft VS Code: `memory-leak-audit` — https://github.com/microsoft/vscode/blob/main/.github/skills/memory-leak-audit/SKILL.md

- **Kind:** Project skill (SKILL.md) inside a large TypeScript codebase.
- **Signals:** VS Code has 192.8K stars. File last changed 2026-05-29. skills.sh: 3.0K installs.
- **Scope and structure:** 5.7 KB. A 6-step audit in a fixed order, then a quick-reference table and a verification section. **Each rule cites the pull request that proved it**, for example "185 listeners leaked after 37 toggles".
- **Trigger:** Reviewing event listeners, DOM handlers or lifecycle callbacks, or fixing leak reports.
- **Strong rules (paraphrased, in framework-neutral words):**
  - A listener added inside a method that runs many times must belong to a per-call disposable that replaces the previous one. It must not go into the class-lifetime store. In plain DOM, this is one AbortController for each call.
  - Listen to one-time lifecycle events with a once-only subscription.
  - In pools, cleanup belongs to each item, not to the pool.
  - Tests must fail on leaked disposables. VS Code has a test helper for this.
  - To confirm a leak, force GC between N repetitions, fit a line to the heap and DOM samples, and flag growth per operation above a threshold (VS Code uses 2 MB per chat message).
- **Weak points:** The helper names are specific to VS Code. It says nothing about GPU resources or canvas contexts.

## patterns.dev: `js-performance-patterns` — https://github.com/patternsdev/skills/blob/main/javascript/js-performance-patterns/SKILL.md

- **Kind:** Claude skill (SKILL.md), from the patterns.dev authors.

## dembrandt: `performance-and-web-vitals` — https://github.com/dembrandt/dembrandt-skills/blob/main/skills/performance-and-web-vitals/SKILL.md

- **Kind:** Claude skill with extra metadata (`pathPatterns`, `promptSignals`, `retrieval.intents`) for a custom retrieval tool. Claude Code ignores these keys (they are not the standard `paths` field).
- **Signals:** 56 stars. File last changed 2026-04-19. skills.sh: 771 installs.
- **Scope and structure:** 8 KB, classified **by metric**, then images, fonts and JS, then a review checklist.
- **Weak points:** For INP it suggests `requestIdleCallback` for heavy work, which delays non-urgent work but does not shorten an interaction. ## Design lessons for our skill

1. **Triggering is the main risk for a "while writing code" skill.** Vercel measured 56% non-invocation with default triggering. Use three layers:
   - a 2–4 line pointer in the project CLAUDE.md or AGENTS.md ("before writing or changing HTML/CSS/TS render or chart code, read the web-performance skill");
   - `paths:` globs (`**/*.{ts,tsx,svelte,css,html}`), which Claude Code uses to limit auto-activation to matching files (it is not a force trigger);
   - a description that starts with the writing task ("Use when writing or changing …") and not with audit phrases, within the 1,536-character cap.
2. **Order the steps: explore, then consult.** Tell the agent to read the target code and the installed library typings first, and then apply the skill. This beat "MUST invoke first" in Vercel's evals. Chrome's "MANDATORY: execute first" style is the counter-example.
3. **Classify by pipeline stage, and keep a small glossary.** Following ibelick, the stages are network/load, parse/script, style/layout, paint/composite, GPU upload/draw, and memory/lifecycle. Give each stage one reference file, one level deep, loaded on demand. Keep SKILL.md to a stage map plus the "never" rules (Anthropic: under 500 lines; ibelick shows 5.6 KB is enough for one stage family).
4. **Give every rule the same shape:** impact tag, one-line reason, a wrong/right code pair, and **how to verify** (a trace insight, a test assertion or a DevTools check). Sources: Vercel impact tags, PixiJS `[CRITICAL]` tags plus a "Source:" line, and ibelick's review output (quoted line, why, fix).
5. **Tie each rule to evidence.** Cite a doc, a spec or an incident (VS Code "Validated by PR #…"). Label static findings as hypotheses until they are measured (web-quality-skills, see the sibling survey). Use a conservative review stance: fewer, stronger findings, and silence over nitpicks (Front-End Checklist).
6. **Treat freshness as a feature.** Keep version-sensitive facts (Baseline status, deprecations, browser versions) in one reference file with a "verified on" date and source links, and keep the rules free of dates (Anthropic "old patterns"). Adopt Chrome's Baseline policy: Widely available is safe; anything else needs the stated fallback. The evidence that this matters:
   - four popular marketplace entries still cite FID more than two years after INP replaced it;
   - Vercel's own agent still points to the deprecated `priority` prop;
   - Chrome's own guide is stale on bfcache and `no-store`.
7. **Library facts come from the installed package.** Following TradingView: print the installed version, grep the typings, and treat an API name that is not in the typings as nonexistent. Write symptom, suspect, verify, fix recipes for the common chart failures (snapping view, jank on tick, leak on remount).
8. **Name the agent's default mistakes explicitly.** Examples: the "happy path only" code from Mapbox (no error handler, no teardown, tiny test data), a new dependency where a platform API exists, `setTimeout` used to sync animations, synchronous filtering of large lists, and replacing the whole dataset on each tick. A short "agent defaults to avoid" list costs little context and targets the real gaps (Chrome prunes guidance that models already follow).
9. **Verify with measurement tools, not scores.**
   - Chrome DevTools MCP traces plus `performance_analyze_insight`, with CPU throttling set through `emulate`. Its `lighthouse_audit` has no performance category.
   - Save traces to files, and never paste raw traces into the context (Dallacqua).
   - Use field data for INP (Karel).
   - Use fixed scripts instead of improvised measurement code (issue #1114, nucliweb).
10. **Evaluate the skill.** Write at least 3 eval tasks whose prompts do not name the API (Chrome: "make my images load faster"). Grade with deterministic checks (a Playwright or unit assertion, a trace insight). Calibrate each grader on a good page and a bad page, and track the uplift with and without the skill (Chrome Modern Web Guidance: +22 to +35 points). Also keep the scope boundary: do not migrate libraries; apply the rules inside the existing stack (ibelick).

## Rules to consider adding

1. **Pause off-screen renderers.** Put `content-visibility: auto` + `contain-intrinsic-size: auto <h>` on each chart panel. Stop the render loop and data subscription when `contentvisibilityautostatechange` reports `event.skipped === true`, and resume when it reports false. Listen on the element itself, not through bubbling. Use IntersectionObserver as the fallback. — https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/performance/efficient-background-processing.md
   ```ts
   panel.addEventListener('contentvisibilityautostatechange', (e) => {
     (e as ContentVisibilityAutoStateChangeEvent).skipped ? chart.pause() : chart.resume();
   });
   ```
2. **Contain self-contained regions that stay on screen** (watchlists, order-book columns, panel grids) with `content-visibility: auto` (it adds layout, style and paint containment), so a change inside one region does not trigger a page-wide layout. Fallback: `contain: layout style paint`. — https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/performance/interactions-in-complex-layouts.md
3. **Yield on a time deadline, not on an item count.** Yield when `performance.now()` passes 50 ms since the last yield. Feature-detect `scheduler.yield` (Chrome 129, Firefox 142, no Safari). — https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/performance/break-up-long-tasks.md
   ```ts
   let deadline = performance.now() + 50;
   for (const tick of ticks) {
     apply(tick);
     if (performance.now() > deadline) {
       await ('scheduler' in globalThis && 'yield' in scheduler ? scheduler.yield() : new Promise((r) => setTimeout(r)));
       deadline = performance.now() + 50;
     }
   }
   ```
4. **Size the work before you pick where to run it.** Under 50 ms: run it in place. 50–250 ms: slice it and yield. Over 250 ms (indicator math over long history, large re-bucketing): run it in a Web Worker. — https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/performance/performance.md
5. **Update realtime series incrementally.** Append or replace only the last point on each tick. Rebuild the whole dataset only on a real replace (for example a symbol change), and save and restore the visible range around that rebuild. — https://github.com/tradingview/lightweight-charts/blob/master/.github/skills/lightweight-charts/SKILL.md
6. **One chart instance per mount.** Create the chart once in the mount hook and destroy it in cleanup (the chart library's delete or remove call). Never recreate it in a reactive block that reruns. Verify: mount and unmount 20 times, then the canvas count and the listener count return to the baseline. — https://github.com/tradingview/lightweight-charts/blob/master/.github/skills/lightweight-charts/SKILL.md and https://github.com/mapbox/mapbox-agent-skills/blob/main/skills/mapbox-web-performance-patterns/SKILL.md
7. **Size a custom canvas in device pixels.** Observe it with `ResizeObserver` using `{ box: 'device-pixel-content-box' }`. Fall back to `Math.round(contentRect × devicePixelRatio)`. Do not poll the size in the render loop. — https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/visual-design/apply-webgl-shaders.md
8. **Update GPU-drawn text only on change.** Text drawn through a 2D canvas is re-rasterized and re-uploaded each time it changes. Compare with the old value before you set it, and use atlas or bitmap text for per-frame counters. — https://github.com/pixijs/pixijs-skills/blob/main/skills/pixijs-performance/SKILL.md
9. **Keep GPU uploads off the first frame and off hot frames.** Upload before the first visible frame, upload only changed byte ranges of large buffers, and spread bulk destruction over several frames. — https://github.com/pixijs/pixijs-skills/blob/main/skills/pixijs-performance/SKILL.md
10. **Order draws to keep batches, and use the cheapest clip.** Group objects of the same kind and blend mode. Use axis-aligned rectangle (scissor) clips before stencil or alpha masks. — https://github.com/pixijs/pixijs-skills/blob/main/skills/pixijs-performance/SKILL.md
11. **Treat DPR, antialias and `preserveDrawingBuffer` as costs.** DPR 2 means 4 times the fragments. Turn on antialias or `preserveDrawingBuffer` only for a stated need (for example a screenshot export), and decide on target hardware. — https://github.com/pixijs/pixijs-skills/blob/main/skills/pixijs-performance/SKILL.md and https://github.com/mapbox/mapbox-agent-skills/blob/main/skills/mapbox-web-performance-patterns/SKILL.md
12. **Listener ownership follows call frequency.** A listener added in a method that runs many times gets one AbortController per call, and each new call aborts the previous controller. Never add it to a store that lives as long as the component. Listen to one-time lifecycle events once. — https://github.com/microsoft/vscode/blob/main/.github/skills/memory-leak-audit/SKILL.md
13. **Prove a leak fix by slope.** Repeat the operation N times with a forced GC between repetitions, sample the heap and the DOM node count, and fail when the growth per repetition is over a threshold. A single before/after snapshot is not proof. — https://github.com/microsoft/vscode/blob/main/.github/skills/memory-leak-audit/SKILL.md
14. **Do not animate custom properties that feed transform or opacity, and do not animate inherited custom properties.** Every frame then invalidates style for the whole subtree. Animate `transform` or `opacity` directly, and scope variables locally. — https://github.com/ibelick/ui-skills/blob/main/skills/fixing-motion-performance/SKILL.md
15. **Every rAF loop has a stop condition, and one element has one animation owner.** Do not let two systems each measure and change the same element's layout. — https://github.com/ibelick/ui-skills/blob/main/skills/fixing-motion-performance/SKILL.md
16. **SVG or DOM charts: freeze geometry after the enter animation.** Animate hover with transform or opacity on a group. Keep hover state separate from data and geometry state, so a hover does not recompute paths. — https://github.com/bklit/bklit-ui/blob/main/.agents/skills/bklit-studio-chart-performance/SKILL.md
17. **SPA route changes should count as soft navigations.** Start the route change from a user action, change the URL with the Navigation or History API, and paint. Chrome 151+ then reports `soft-navigation` and `interaction-contentful-paint` entries for each route. Feature-detect with `PerformanceObserver.supportedEntryTypes`. — https://developer.chrome.com/docs/web-platform/soft-navigations
18. **Keep the terminal bfcache-eligible.** Chrome evicts `no-store` pages that use WebSocket, WebTransport or WebRTC. Close live feeds on `pagehide` and reconnect on `pageshow` when `event.persisted` is true. — https://developer.chrome.com/docs/web-platform/bfcache-ccns
19. **Resilient live feeds.** Pick the transport by direction (SSE for one-way push, WebSocket for two-way). Send heartbeats, and reconnect with capped exponential backoff while queuing outgoing messages. — https://github.com/wondelai/skills/blob/main/high-perf-browser/SKILL.md
20. **No happy-path-only render code.** Every generated chart or map needs an error path, a teardown path, and a test or demo at realistic scale (thousands to millions of points, not 10). — https://github.com/mapbox/mapbox-agent-skills/blob/main/skills/mapbox-web-performance-patterns/SKILL.md
