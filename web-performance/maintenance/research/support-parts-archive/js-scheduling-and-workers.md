Facts that the rules state without a version, for references/support.md §C (engine and tool facts):

- Nested timer clamp (TASK-05, §0): Chromium follows the HTML timer steps. `kSpecCompliantMaxTimerNestingLevel = 6`, the level is incremented before use, and `kMinimumInterval = 4 ms`, so a timer nested more than 5 deep waits at least 4 ms. Chrome removed the separate 1 ms minimum for `setTimeout(0)` in Chrome 101 and for `setInterval` in Chrome 135. Sources: https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/scheduler/dom_timer.cc ; https://chromestatus.com/feature/4889002157015040 ; https://chromestatus.com/feature/5072451480059904
- Hidden-tab timers (TASK-09, §0): after about 10 s hidden (`kThrottlingDelayAfterBackgrounding`), Chromium aligns timers to one wake-up per second. Intensive wake-up throttling (one wake-up per minute for chained timers with chain count 5 or more, in silent pages without WebRTC) starts after **1 minute** hidden for pages that finished loading (`kIntensiveWakeUpThrottling_GracePeriodSecondsLoaded_Default = 60`) and after 5 minutes for pages that are still loading. It started in Chrome 88. An open WebSocket gives no exemption (`websocket_channel_impl.cc` does not opt out). Enterprise policy `IntensiveWakeUpThrottlingEnabled` can turn it off or force it on. Sources: https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/platform/scheduler/common/features.cc ; https://developer.chrome.com/blog/timer-throttling-in-chrome-88 ; https://chromeenterprise.google/policies/intensive-wake-up-throttling-enabled/
- Freezing on Energy Saver (TASK-09 Avoid: "late or frozen"): from Chrome 133, with Energy Saver on, Chrome freezes a CPU-heavy browsing context group that has been hidden and silent for more than 5 minutes; all tasks stop, WebSocket handling too. Opt-out origin trial `BackgroundPageFreezeOptOut`. Source: https://developer.chrome.com/blog/freezing-on-energy-saver
- Deferred and module scripts get their own tasks (TASK-06): from Chrome 145, Chromium runs each deferred classic script and each module script in its own task (runtime flag `SeparateDeferModuleScriptTasks`, stable; commit e7e02f3c). Chrome 144 and older ran all of them in the `DOMContentLoaded` task. The web.dev article is out of date on this point. Conflict: `verify/06` found no source for a change, `verify/01-critical-rendering-path.run2-new` found the commit; the commit wins. Sources: https://chromiumdash.appspot.com/commit/e7e02f3ceba01c4519f58ab4b4c2445ba7566609 ; https://web.dev/articles/script-evaluation-and-long-tasks
- `performance.now()` resolution in Chromium (TASK-02 says only "coarsened"): 100 µs, or 5 µs when cross-origin isolated. Firefox and WebKit use other values (1 ms by default, 20 µs isolated). Source: https://developer.mozilla.org/en-US/docs/Web/API/Performance/now
- Wasm deoptimization (TASK-13 Avoid): V8 shipped Wasm deopts with speculative `call_indirect` inlining in Chrome 137 (enabled 2025-04-07; `wasm_deopts_per_function_limit = 10`). Source: https://v8.dev/blog/wasm-speculative-optimizations
- Wasm code cache (TASK-14 Why): Chrome caches only TurboFan code; a caching event fires when enough new top-tier code exists (V8 `main`: `wasm_caching_threshold` 1,000, `wasm_caching_timeout_ms` 2,000, hard threshold 1,000,000), so the 2019 "128 kB" rule is obsolete. Liftoff code is never cached. `Version::Hash()` includes the V8 patch number, so each milestone (every 2 weeks from Chrome 153) and most weekly security updates cause one cold compile per user. Sources: https://v8.dev/docs/wasm-compilation-pipeline ; https://github.com/v8/v8/blob/main/src/flags/flag-definitions.h ; https://developer.chrome.com/blog/chrome-two-week-release
- Wasm features that TASK-14 names without a row (Chromium only matters): relaxed SIMD Chrome 114, limited (results can differ by CPU); Memory64 Chrome 133, limited; JSPI Chrome 137, newly available since 2026-09-14 (not used by a rule). Source: https://cdn.jsdelivr.net/npm/web-features/data.json

For references/support.md §E (do not use): `navigator.scheduling.isInputPending()` (Chromium 87 only; web-features `is-input-pending` is "discouraged", MDN shows a Deprecated banner while BCD still has `deprecated: false`; web.dev reversed its advice in October 2024); `setImmediate` (legacy Edge only); `requestPostAnimationFrame` (a proposal, not in BCD); options to `scheduler.yield()` (removed from the spec).

For references/support.md §F (myths), each already corrected in a TASK rule: "`await` yields to the browser" (TASK-04); "`setTimeout(fn, 0)` runs next" (TASK-05; it runs after queued tasks, with the nested clamp); "`requestIdleCallback` shortens an interaction" (TASK-07); "workers make code faster" (TASK-10); "`JSON.stringify` before `postMessage` is faster" (no clear winner in Surma's measurements; TASK-11 keeps plain `postMessage`); "Wasm is always faster" (TASK-13).
