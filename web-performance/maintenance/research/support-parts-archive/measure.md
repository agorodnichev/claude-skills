Facts for references/support.md §C (engine and tool facts):

- **chrome-devtools-mcp version.** npm `latest` is 1.10.1 (published 2026-09-23 10:42 UTC; 1.10.0 the same day). The research notes were written against 1.9.0 (2026-09-08). The behavior that measure.md uses is unchanged in 1.10.1. `get_css_styles` came in 1.10.0. `analyze_heapsnapshot_contexts` is on `main` only, not in 1.10.1, so measure.md does not name it. Source: https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/CHANGELOG.md ; verify/14 header.

- **Traces in 1.10.1.** `reload: true` goes to `about:blank`, starts tracing, loads the URL, waits for `load`, then waits a fixed 5 s and stops. One trace at a time ("Only one trace can be running at any given time."). `performance_analyze_insight` reads only the last trace. Set ids are `NAVIGATION_<n>` (soft navigations too) or `NO_NAVIGATION`. The summary prints `CPU throttling: <n>x` and `Network throttling: <preset or none>` as they are at stop time, LCP and subparts, INP, CLS, insights, CrUX field metrics (`scope: url|origin`) and "# Custom tracks"; it prints no TBT, FCP, frame, FPS or GPU data. `SlowCSSSelector` is never listed (MCP turns on only the JS-sampling and screenshot optional categories). Default trace buffer 1.2 GB since 1.9.0; chunked trace parser in 1.10.0. `navigate_page` removes its `initScript` after its own navigation, so it does not reach the trace's reload. A saved trace has no `cpuThrottling` or `networkThrottling` metadata keys (kit check).
- **The 19 insight names** (devtools-frontend `Models.ts`): `LCPBreakdown`, `LCPDiscovery`, `RenderBlocking`, `NetworkDependencyTree`, `DocumentLatency`, `ImageDelivery`, `ModernHTTP`, `DuplicatedJavaScript`, `LegacyJavaScript`, `ThirdParties`, `Cache`, `FontDisplay`, `CharacterSet`, `CLSCulprits`, `INPBreakdown`, `DOMSize`, `ForcedReflow`, `SlowCSSSelector`, `Viewport`. measure.md points to pipeline.md §I for the insight → stage table.
- **`emulate` in 1.10.1.** An omitted option is reset (CPU rate 1, network off, viewport, user agent and color scheme cleared; geolocation set to 0,0); `extraHttpHeaders` persists until cleared. Emulation is stored per page. A change of the `mobile` or `touch` flags can reload the page (Puppeteer `EmulationManager`). In the kit check (Chrome 153), `emulate` emptied `navigator.userAgentData` (no brands, no platform).
- **`lighthouse_audit`** runs only accessibility, SEO, best-practices and agentic-browsing (it "excludes performance"); Lighthouse 13.4.1 is bundled in 1.10.1; mobile 412×823 at DSF 1.75, desktop 1350×940 at DSF 1.
- **Debugger tier-down.** MCP creates a DevTools target universe per page that auto-starts `DebuggerModel` (`Debugger.enable`), and V8 then moves wasm to Liftoff debug code. Found by reading chrome-devtools-mcp 1.10.1, devtools-frontend and V8 source (15-gaps-round-1, unchecked there; confirmed as a caveat in verify/14 "Missing" 1 and verify/13 "Missing" 5). The size of the effect is not measured.
- **Console cost with MCP attached.** About 4.9 µs per `console.timeStamp` call against about 0.15 µs without an inspector (headless Chrome 153, 100,000 calls; 15-gaps-round-2, unchecked). The extended `console.timeStamp(label, start, end, track, group, color)` signature is from Chrome 134 (a DevTools convention).
- **Network emulation and WebSockets.** DevTools throttles WebSocket bandwidth and the handshake (since Chrome 99), not the latency of each message (live run on Chrome 153, 15-gaps-round-2, unchecked).
- **Kit check environment** (the "kit check" numbers in measure.md): 2026-09-23; Google Chrome 153.0.8010.53, headed, started by chrome-devtools-mcp with `--enable-features=WebMCP`; Mac16,5, Apple M4 Max, 16 cores, macOS 27.0.0, 120 Hz display; WebGL `ANGLE (Apple, ANGLE Metal Renderer: Apple M4 Max, Unspecified Version)`; WebGPU `apple/metal-3` (not the fallback adapter); profile `emulate {cpuThrottlingRate: 4, viewport: "1440x900x2"}`, network off; `scripts/probes.js` VERSION 2.
- **WebMCP behavior seen in the kit check (Chrome 153).** `execute` receives `(input, { signal })`. Chrome did not check input against `inputSchema` enums. A thrown error reached `execute_webmcp_tool` as `{"status":"Error","errorText":""}`, so the template returns `{ error }`. A page-side `document.modelContext.executeTool()` needed a JSON string (an object gave "Failed to parse input arguments"); Chrome documents JSON-string input as deprecated from Chrome 155, so re-check this on a newer build. `list_webmcp_tools` echoed `readOnly: true` for `readOnlyHint`. The `execute_webmcp_tool` status enum is `Completed | Canceled | Error` (CDP `InvocationStatus`).
- **Event Timing rounding.** Durations are rounded to 8 ms (kit check: 168, 176, 32 ms).
