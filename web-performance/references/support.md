## Chromium floor

- **Target:** Chromium only (Chrome and Edge). The rules ship no fallback code for Firefox or Safari. Their status in §A is information only, and a Baseline status alone never decides what to write.
- **Floor: Chrome 140 and Edge 140** (stable on 2025-09-02 and 2025-09-05 per BCD), about 12 months of releases before the check date. Both browsers update themselves, and Chrome's Extended Stable channel moves every 8 weeks, so a 12-month floor leaves a wide margin.
- **The "At the floor" column of §A** says what code to write:
  - `use`: Chromium 140 has it. Use it with no detection and no fallback.
  - `detect`: newer than the floor. Feature-detect it and ship the fallback that the row names.
  - `gated`: Chromium 140 has it, but a GPU, driver, platform, secure context or cross-origin isolation can still remove it. Check at run time at any floor.
  - `engine`: an engine behavior. There is nothing to detect; the row says how releases between the floor and the listed version differ.
  - `not shipped`: not in stable Chromium. Do not ship code that depends on it.
- **A project floor wins** (browserslist, AGENTS.md, CLAUDE.md, or what the user says). With another floor, compare each row's Chrome version with it. At each refresh, move the default floor to the release about 12 months back and update the column.

## §B Chromium-only APIs and V8 internals

No fallback code is needed. Chromium-only APIs with a §A row: `long-animation-frames`, `layout-instability`, `measure-memory`, `compute-pressure`, `not-restored-reasons`, `page-lifecycle`, `fetch-later`, `explicit-compile-hints`.
- **Element Timing** (`elementtiming`, `element` entries): Chrome 77, experimental. Canvas content is not timing-eligible. Since Chrome 133, a cross-origin image without `Timing-Allow-Origin` gets a `renderTime` coarsened to 4 ms steps, not 0.
- **JS Self-Profiling** (`new Profiler()`, needs `Document-Policy: js-profiling`): Chrome 94, experimental.
- **`performance.now()`**: Chromium rounds it to 100 µs, or 5 µs when the page is cross-origin isolated.

V8 internals change between releases; v8-hot-code.md states the rules without these numbers.
- **`JSON.stringify` fast path** (Chrome 138+): only with no replacer and no `space`, on plain objects (initial `Object.prototype`, fast properties, no elements), plain arrays and primitives; any other value restarts the call on the slow path. `JSON.parse` reuses the previous sibling's map, has a fast path for arrays of same-shape objects since Chrome 152, and detects a two-parameter reviver since Chrome 143 (still about 5 times slower than none).
- **Inline caches:** the polymorphic limit is 4 maps through Chrome 153 and 10 from Chrome 154. A "homomorphic" state (many maps, one handler) is behind `--homomorphic-ic` since Chrome 147 and on by default from Chrome 156. `--log-ic` states: `0` uninitialized, `1` monomorphic, `P` polymorphic, `H` homomorphic, `N` megamorphic, `D` MegaDOM, `G` generic, `X` no feedback, `^` recompute. Analyzer: https://v8.github.io/tools/head/system-analyzer/
- **Dictionary mode:** every `delete` since Chrome 122 (the fast path for the last-added property is gone); also computed-key stores past 12 out-of-object fields, 1,020 own descriptors, literals and `JSON.parse` objects with 128 or more keys, and `Object.create(null)`.
- **Pointer compression** (Chrome 80+, 64-bit desktop and Android): 4-byte tagged slots, 31-bit small integers (about ±1.07 billion). Official Node builds do not compress: 8-byte slots, 32-bit small integers.
- **Elements kinds:** about 40 in V8; six fast kinds matter (packed or holey × small integer, double, any). Since Chrome 135, `fill()` over a whole array with its initial map moves it to the best packed kind.
- **Regular expressions:** from Chrome 152, a new pattern compiles to native code on first use (79–151 interpreted it first). The linear-time engine is an experimental flag, off by default.
- **Sort:** stable (TimSort from Chrome 70, PowerSort from 149). Since 149, packed arrays of 16 elements or fewer with a comparator known at the call site use an inlined insertion sort; since 153 all receiver maps must share one elements kind. The default typed-array sort is not stable.
- **`Object.assign({}, src)`** takes a fast clone path since Chrome 129 when the target is a fresh empty object and the source is a plain fast object.
- **BigInt:** TurboFan lowers 64-bit operations since Chrome 108 and keeps `BigInt64Array` values unboxed since 111; Maglev specializes BigInt since 151. Code that is not optimized allocates a BigInt per operation.
- **Tiers** (V8 `main`): Sparkplug after about 8 calls, Maglev after about 400 (1,000 on Android), TurboFan after about 3,000; loops tier up by on-stack replacement. Turbolev is off.
- **`Intl`:** V8 caches one ICU object per kind, only when `locales` is a string or `undefined` and `options` is `undefined`, and keeps only the latest entry per kind. `NumberFormat.formatRange` Chrome 106; `DateTimeFormat.formatRange` Chrome 76.
- **Stack traces:** source positions are lazy, so the first `.stack` of a function reparses it. `Error.stackTraceLimit` (default 10) is non-standard.
- **Optimization off:** the site setting "JavaScript optimization & security" (Chrome 133+) is off by default for Advanced Protection users; then V8 runs no Maglev or TurboFan, and Wasm runs Liftoff code only (V8-17).
- **iOS:** Chrome and Edge on iOS use WebKit and JavaScriptCore, not V8 (App Store guideline 2.5.6), so no V8 fact here applies there.

## §C Engine and tool facts

### Chromium engine
- **Tasks and timers:** a timer nested more than 5 levels waits at least 4 ms. Chrome removed its extra 1 ms minimum for `setTimeout(0)` in 101 and for `setInterval` in 135. Continuous input (`pointermove`, `mousemove`, `touchmove`, `wheel`) is dispatched just before rAF. rAF works in dedicated workers since 69, not in nested workers. Layerize runs on the renderer main thread. The network service has its own process, except on Android.
- **CSS and input:** size containers stopped applying layout containment in 129 (add `contain: layout` where a container must isolate layout). `commitStyles()` without a fill works from 144, so CSS-17 keeps `fill: 'forwards'` below that. `text-wrap: balance` balances only blocks of six lines or fewer. `overscroll-behavior` also applies to containers without scrollable overflow from 144. Touch listeners (55) and wheel listeners (73) on window, document, `<html>` and `<body>` are passive by default. `pointerrawupdate` needs a secure context from 142.
- **Hidden pages:** after about 10 s hidden, timers align to 1 s wake-ups. Intensive throttling (1 wake-up per minute for chains of 5 or more timers, in silent pages without WebRTC) starts after 1 minute hidden for loaded pages and 5 minutes for pages still loading (since Chrome 88). An open WebSocket gives no exemption. The enterprise policy `IntensiveWakeUpThrottlingEnabled` turns it off or on.
- **Energy Saver** (133+): freezes a hidden, silent, CPU-heavy browsing context group after 5 minutes; all tasks stop, WebSocket handling too. Opt-out origin trial: `BackgroundPageFreezeOptOut`. Energy Saver also lowers the frame rate.
- **bfcache:** `Cache-Control: no-store` pages became eligible over March–April 2025, with a 3-minute limit (10 minutes for other pages) and eviction on cookie or authorization changes. From 149 (the blink-dev PSA says 148), Chrome closes open WebSockets when a page enters the bfcache and fires `error` and `close` on restore, instead of blocking; the policy `BackForwardCacheForWebSocketsAllowed` = Disabled restores blocking. On a `no-store` page any WebSocket use blocks, even after close. Firefox still blocks on open WebSockets.
- **`unload`:** Chrome's rollout table plans `unload` off by default for 100% of page loads at Chrome 154. The table says "subject to change", and no source confirms that the last step shipped. Opt back in only with `Permissions-Policy: unload=(self)` or the enterprise policy `ForcePermissionPolicyUnloadDefaultEnabled`.
- **Storage:** IndexedDB, Cache Storage and OPFS share one origin quota (Chromium: up to 60% of the disk per origin); `localStorage` has its own 5 MiB. Eviction is least recently used, by whole origin. Each opaque response in Cache Storage is padded by 0 to about 14 MiB of quota. IndexedDB's default durability is relaxed since 121. All in-flight `keepalive` bodies share 64 KiB.
- **Loading:** in tight mode (until `<body>` exists), a low-priority request starts only while fewer than two requests are in flight. Since 117, the first 5 images over 10,000 px² start at Medium; an explicit `fetchpriority` turns the boost off. `rel=preload` in a `Link` header of a subresource response is ignored; an unused preload warns 3 s after `load`. An unused preconnected socket closes after about 60 s (not 10 s), a used idle socket after 300 s, an idle QUIC connection after 30 s. 103 Early Hints (103+) work only over HTTP/2 or HTTP/3, for navigations, from the first 103 only; a cross-origin redirect drops them. HTTP/2 push is off since 106. Lazy-load distances: images 1250 px on 4G and 2500 px on 3G; frames 2500 and 3500 px. `Document-Policy: expect-no-linked-resources` ships since 134 (no rule uses it).
- **HTML and network:** `blocking="render"` 105; `<link rel="expect">` 124 (experimental); `No-Vary-Search` in the HTTP cache 141 on desktop and 143 on Android (speculation prefetch 121, prerender 127); zstd content encoding 123 (newly available 2026-02-11; keep the window at 8 MB or less, RFC 9659). Server-sent events over HTTP/1.1 get at most 6 connections per browser and domain, across tabs ("Won't fix" in Chrome and Firefox). A service worker costs about 50 ms to start on desktop and 250 ms on mobile; Chrome skips a no-op fetch handler since 115.
- **LCP candidates:** ignored at opacity 0 (86), when they cover the viewport (88), for images under 0.05 bits per displayed pixel (112) and for transparent text (130); a video's first frame counts (116). A cross-origin LCP `renderTime` without `Timing-Allow-Origin` is coarsened since 133, not 0.
- **Code caches:** a JS cache is made on a load within 72 hours of the first; scripts under 1,024 characters and inline scripts get none. Wasm: only TurboFan code is cached, when enough new top-tier code exists (V8 flag `wasm_caching_threshold`, default 1,000) or after a 2 s timeout; Liftoff code never is. The 2019 "modules of 128 kB or more" rule is obsolete (verify/07 and verify/09 read V8 `main`; verify/13 still cites the 2019 post). Every V8 version change, patch number included, drops the JS and Wasm caches. Wasm deopts shipped in 137.
- **GPU:** at most 16 live WebGL contexts per page on desktop, 8 on Android and 4 per worker thread (`--max-active-webgl-contexts` overrides); past the cap, the context with the oldest flush is lost, and an evicted context returns only when a slot frees. From 139, Chrome desktop has no SwiftShader fallback: `getContext('webgl2')` returns `null` without a usable GPU (Windows keeps a software path only for devices with no GPU or a blocklisted GPU). After 2 GPU-process crashes within 2 minutes Chrome blocks new adapters for the page, after 3 for all pages; a shader that runs about 10 s trips the watchdog. A second `requestDevice()` on one adapter rejects since 140. `GPUAdapterInfo.isFallbackAdapter` (136) is always false on user devices. On Windows, WebGPU `powerPreference` has no effect. WebGL `finish()` is a flush in Chrome. `GPUUncapturedErrorEvent` fires in workers too.
- **GPU capability shares** (web3dsurvey, WebGL2 reports, read 2026-09-23; the page gives no date window): `MAX_TEXTURE_SIZE` of 4096 or more in 100% and 16384 or more in 86%; `EXT_color_buffer_float` 99.94%; `EXT_float_blend` 93.76%; `EXT_color_buffer_half_float` 92.37%; `OES_texture_float_linear` 90.58%; `WEBGL_provoking_vertex` 76.86%; `MAX_CLIENT_WAIT_TIMEOUT_WEBGL` of 1 s or more 7%.
- **Canvas 2D:** without `willReadFrequently`, an accelerated canvas moves to the CPU after 2 `getImageData` calls (a console warning on the second). Parsed colors live in an 8-entry cache. A hidden page snapshots accelerated canvases to CPU memory after up to 4 minutes and compresses them after 5. Only a canvas in the document forces style updates in `font`, `fillText` and `measureText`. Limits: 65,535 px per side, 16,384² px of area.

## §F Myths (dated corrections)

| Myth | Correction | Source |
|---|---|---|
| "`await` yields to the browser" | it queues a microtask; input and rendering wait until the whole task ends | TASK-04 |
| "`setTimeout(fn, 0)` runs next" | it runs after queued tasks, and at least 4 ms later when nested more than 5 levels | TASK-05 |
| "`requestIdleCallback` shortens an interaction" | it only moves work to after the frame | TASK-07 |
| "Workers make code faster" | they move work off the main thread; messages and startup cost time | TASK-10 |
| "`transform` means no jank" | only compositor-eligible animations skip the main thread; layout reads and main-thread work still drop frames | CSS-01, CSS-03 |
| "A `DocumentFragment` is much faster" / "Wasm is always faster" | the gain is batching the writes; Wasm pays off only for measured kernels that cross the boundary rarely | DOM-07, TASK-13 |
| "`try`/`catch` stops optimization" | not since V8 5.9 (Chrome 59); throwing is the cost | https://v8.dev/blog/launching-ignition-and-turbofan |
| "Cache `array.length` before the loop" | no gain in current JITs unless a profile shows one; `for…of` and `forEach` run about as fast as `for` | https://v8.dev/blog/elements-kinds |
| "`let` and `const` are slower than `var`" | V8 removes redundant TDZ checks (2023) | https://v8.dev/blog/holiday-season-2023 |
| "Spread beats `Object.assign({}, x)`" | both take a fast clone path since Chrome 129 (V8 commit b71404f1c8) | v8-hot-code.md §H |
| "Desugar spread, destructuring and argument padding by hand" | native forms are as fast since V8 7.2 to 8.9 (Chrome 72 to 89) | https://v8.dev/blog/adaptor-frame |
| "Build JSON strings by hand" / "promise chains beat `async`" | `JSON.stringify` is more than twice as fast since Chrome 138; `await` is fast since V8 7.2 (Chrome 72) | https://v8.dev/blog/json-stringify |
| "More than 4 shapes at a site is megamorphic" | the limit is 10 from Chrome 154; still aim for one shape | V8-02 |
| "`JSON.stringify` before `postMessage` is faster" | no clear winner in measurements; post plain data | TASK-11 |
| "Chrome releases every 4 or 6 weeks" | every 2 weeks since Chrome 153, with weekly security updates | https://developer.chrome.com/blog/chrome-two-week-release |
| "A preconnected socket closes after 10 s" | about 60 s in Chromium | https://chromium.googlesource.com/chromium/src/+/main/net/socket/client_socket_pool_manager.cc |
| "Debounce scroll handlers" / "`will-change` in base CSS" | throttle visuals with rAF and use `scrollend`; set `will-change` just before the motion | EVT-11, CSS-05 |
